GEAMS security self-review pack

For a security reviewer, or for you before one is hired. It says what GEAMS does to protect itself, how to check that, and, most important, what has not been checked.

This is a self-review, not an audit. The same people who built GEAMS wrote these checks. They show the known protections work; they cannot show there are no other holes. Before real use at national scale, have an independent security professional test the system you actually deploy (your server, your network, your hosting) and fix what they find.

2. Who is trusted for what

  • Civilian phone: trusted only for its own alerts. Proves ownership with a secret kept on the phone (hashed into its token). Cannot read other people's alerts, faces or accounts.
  • Officer / fire / ambulance crew: only their own control room's records (another area answers 403), and officers only the incident assigned to them.
  • Fire HQ / Ambulance HQ: each sees only its own service: the alerts control rooms forwarded to its crews, its own crew list and its own reports. Never police incidents, officers, intel, evidence or the other service. A new HQ account must choose its own password before anything opens. A crew member's HQ messages are readable only by that person and their own HQ. Created, reset and disabled by the HQ owner only (t_agency.js).
  • Control room (station): own station's records and crews. Needs the station passphrase, plus a personal commander account if GEAMS_REQUIRE_COMMANDER_ACCOUNTS=1.
  • HQ: everything except raw server-only keys. HQ owner alone can rotate tokens, lock down, run retention, set legal hold.
  • The server is the only place rules are enforced. The apps' own checks are for convenience; every rule is enforced again on the server.

4. Known gaps and weaknesses (be honest with the reviewer)

GapWhy it mattersWhat to do
The Content-Security-Policy is only partly strict. The apps use inline scripts and click handlers, so the policy has to allow inline script (eval is no longer allowed; the face library ran without it in a desktop test, not yet on real phones; GEAMS_CSP_EVAL=1 restores it).The policy does stop: scripts loaded from other sites, data being sent to any site other than this server and the map, route and search hosts, plugins, extra <base> tags, framing by other sites, and forms posting elsewhere. It does not stop script injected inline into a page, which is still the main risk.Reviewer should test for script injection in every field shown to others. Longer term: move scripts and click handlers out of the pages, then remove 'unsafe-inline' (about 860 inline handlers plus ones built in code; deferred). Violations are reported to HQ > App errors. GEAMS_CSP=report logs without blocking; off disables.
Sign-in tokens are kept in the browser (session storage) and sent as a header.Script injection (above) could read one.Same as above. Tokens expire (12 h staff, 7 days civilians) and can all be revoked with Rotate tokens.
Cross-origin access is open to every site by default.Sign-in is by header, not cookie, so a foreign site cannot use someone's session, but it is wider than needed.Set GEAMS_ALLOWED_ORIGIN to your real site address.
Anyone can send an app-error report (/api/clientlog) and ask for an app's version (/api/version).A flood could fill the error list or hide real errors.Limited by address and per page; the list keeps only the latest 500; only HQ can read it.
Restoring an account by phone number trusts the SIM.SIM-swap attackers could take over an account and read its alert history.Tell people to protect their SIM; consider requiring the recovery code only; monitor restores.
Anyone can open the live event stream and see which keys changed and when (not their contents).Leaks activity patterns only.Accept, or require a token on the stream (not done).
Civilian sessions are anonymous (a secret on the phone). The limits are per phone and per network address.An attacker with many phones or addresses could still send many false alerts.Turn on phone verification (GEAMS_REQUIRE_VERIFIED_CIVILIANS=1, needs SMS) and watch the alert volume.
One server process, one signing key, files on one disk.A server break-in gives everything. A disk failure loses data not yet in the database or a backup.Use the database, off-site encrypted backups, and keep the signing key in the host's secret store.
The station passphrase is shared by the people in a control room unless commander accounts are required.Hard to say who did what.Require personal commander accounts.
Face matching can be wrong and can be unfair across skin tones and lighting.A false match could harm a person.It is shown only as a guide, every check is logged, and HQ reviews the log. Train staff.
Not tested: PostgreSQL, SMS gateway, Ghana Post lookup, outside timestamp, off-site backup, real HTTPS/proxy setup, real phones.Security of those depends on your configuration.Test them in your environment.
Dependencies (map library, face model) are copied into vendor/ and not automatically updated.Known flaws in old versions would stay.Check the library versions in vendor/ against their published security notices before launch.
No penetration test, no code audit by an outsider, no review of your hosting.Unknown problems remain.Commission one.

6. Questions to put to the reviewer

  1. Can you get any civilian's name, phone, Ghana Card or face data without being that civilian or an authorised staff member?
  2. Can you read or change another control room's incidents, crews or evidence?
  3. Can you inject script through any field a staff member will see?
  4. Can you make the server unavailable with a modest number of requests?
  5. Can you forge, reuse or extend a sign-in after it should be revoked?
  6. Can you recover any secret from backups, logs or error messages?
  7. Is the deployment (HTTPS, firewall, database access, secret handling) set up safely?

7. If something is found

  1. HQ owner: Lockdown if it is being used against you; Rotate tokens if sign-ins may be stolen.
  2. Take a backup before changing anything.
  3. Write down what, when, who found it, what data might be affected.
  4. Telling the Data Protection Commission and affected people may be a legal duty [LAWYER].
